## 2026-08-31 — Stage A: actual schema differs from PROJECT.md §9.3's description (as flagged in advance)

**Checked, not assumed** (§2.10): opened the real file rather than trusting PROJECT.md §9.3's description of the raw London Datastore layout.

**Finding:** the file is **wide format**, not the long format (`LCLid`, `stdorToU`, `DateTime`, `KWH/hh`, `Acorn`, `Acorn_grouped`) that PROJECT.md §9.3 describes for the raw London Datastore release. Actual structure: one `DateTime` column + 4,443 household columns (`MAC000002` … `MAC005567`), one row per half-hour timestamp, cell values are that household's kWh reading. **No `Acorn`, `Acorn_grouped`, or `stdorToU` columns exist in this file at all.** Household count (4,443) matches the 4TU page's stated figure exactly, confirming this is genuinely the Std-tariff-filtered refactor, not a different or corrupted release — but the tariff filter was applied *before* this file was produced, so there is no per-row field left to independently re-verify it from the file itself; that check would require the original London Datastore file, not this one.

**Consequence:** `src/schema.py`'s `RAW_SCHEMA` (written before this file arrived) was wrong for the actual artifact. Rewritten against the real structure. Also: "gap detection" as METHODOLOGY.md §1.1 describes it (missing timestamps *per household*) doesn't apply here — the timestamp grid is shared and complete (see next entry) — so the equivalent per-household integrity check here is missing-*value* fraction within an otherwise-complete grid, not missing-*row* detection. This is a real deviation from the written methodology's assumed data shape, logged rather than silently reinterpreted.

**Ingestion note:** the wide 560MB CSV could not be pivoted to long format in one pass on this machine (3.9GB RAM total, ~3.5GB free) — two attempts (whole-frame lazy transform, then a full-width streaming unpivot) both hit OOM. Resolved by batching: 23 batches of ~200 household columns each, relying on Polars' projection pushdown to only parse the needed columns per pass, each batch written to its own parquet part, then concatenated. Total time 46.6s. Output: `data/intermediate/lcl_2013_long.parquet` (136MB, 77,841,360 rows = 4,443 households × 17,520 half-hours, confirmed exact).

## 2026-08-31 — Coarse screen (METHODOLOGY.md 1.2.1)

Filter: overnight (23:00–07:00) mean kW > 1.5 AND overnight/daytime mean-kW ratio > 1.0. The absolute threshold is METHODOLOGY.md's own example value (§9.5 item 2, untested). The ratio cutoff of 1.0 is a decision made here, not specified in METHODOLOGY.md — chosen as the simplest, most auditable interpretation of "unusually high relative to the whole panel" (a household drawing more power overnight than during the day is itself unusual for ordinary consumption), rather than a population-percentile cutoff, which would make the threshold circular against the very population being screened. Logged as an assumption, not a derived result.

**Result: 42 of 4,411 households with any data pass the coarse screen (~1.0%).** Flagged, not yet interpreted — a low hit rate is consistent with either (a) low genuine storage-heater/Economy-7 prevalence in this sample (plausible: this is a Greater London sample, and London's housing stock leans gas-heated relative to the UK average, so a below-national-average storage-heater share would not be surprising) or (b) the coarse screen being too strict. The pre-mortem check (next entry) is the way to tell these apart, not further threshold-tuning.

## 2026-08-31 — Pre-mortem visual check (METHODOLOGY.md 1.2, done BEFORE writing any detector)

Plotted 15 of the 42 coarse-screen-flagged households (top 5, middle 5, bottom 5 by overnight-kW, to sample across the flagged range rather than just the strongest hits), half-hourly kW, 7–16 Jan 2013, with the 23:00–07:00 window shaded. Saved to `data/intermediate/premortem_traces.png`.

**Finding — genuinely mixed, and worth reporting honestly rather than rounding to "it works":**

- **Clean, textbook storage-heater square-wave signature** (steady plateau load confined almost entirely to the shaded overnight window, dropping to near-zero by day, repeating night after night): MAC003218, MAC005198, MAC004863, MAC005041, MAC005009, MAC004902, MAC000415, MAC005216, MAC004983 — 9 of 15. This is the pattern Andy's outline and METHODOLOGY.md §9.5 item 2 predicted, and it is visually unambiguous in these traces — the Sledgehammer Test's core premise holds for this subset.
- **Not a clean storage-heater signature** — spiky, irregular loads with no discrete on/off block (MAC000153, MAC000321, MAC004858), or a near-constant load with no day/night contrast at all (MAC003749, flat ~2kW around the clock — exactly the false-positive risk PROJECT.md §9.9 item 1 names: a load that isn't a storage heater but still trips an overnight-mean threshold, e.g. an immersion heater or continuously-running appliance), or ambiguous/noisy block shapes that don't cleanly separate from daytime activity (MAC005335, MAC001978): 6 of 15.

**Conclusion for next step:** the coarse screen is not clean on its own — roughly 40% of this sample would be false positives if the coarse screen alone were treated as "confirmed storage heater." This is exactly why METHODOLOGY.md §1.2.2's signature confirmation (baseload subtraction, charge-band check, majority-of-nights consistency) is a required second pass, not a formality — proceeding straight from coarse screen to Phase 1's headline finding would overstate prevalence. Not a null result (§2.8) — the pattern is real and strong where it appears — but confirms the two-pass design in the methodology is doing necessary work, and sets an expectation that the confirmed-household count after §1.2.2 will land below 42, not at 42.

## 2026-08-31 — Signature-confirmation detector (METHODOLOGY.md §1.2.2): a real limitation surfaced while self-testing

While writing the self-test for `src/signature_detector.py`, a synthetic fixture with an *identical, invariant charge level every single night* produced zero detected charge-events — not a code bug, but a property of the baseload-subtraction method itself: a rolling 7-day trailing minimum, evaluated at a household that charges the same amount every night without variation, equals the charge level itself, so the residual is zero and nothing looks like a signal.

**Why this matters and why it's flagged rather than quietly patched:** PROJECT.md's own thesis is that unmanaged storage heaters *overcharge on mild nights same as cold ones* — i.e. the failure mode this project is trying to prove is exactly the low-variability charging pattern this detection method would under-detect. This is a genuine tension between METHODOLOGY.md §1.2.2 as written and PROJECT.md's core thesis, not something to paper over. It is only a risk for households whose charging is *very* consistent night-to-night; households with any real night-to-night variation (weather-driven charge duration, meter noise, occasional non-charge nights) are unaffected, and the real data checked below does show that variation. Logged so that if the confirmed-household count looks suspiciously low, this is the first place to look, and so it's on record as a known edge case rather than a surprise found later.

Self-test rebuilt with an alternating charge/no-charge pattern (guarantees genuine baseline contrast within every 7-day window) rather than a constant one, specifically to isolate code-correctness from this separate methodological question. Passes.

## 2026-08-31 — Signature detector run on real data: confirms the predicted failure, v1 abandoned

Ran the detector exactly as METHODOLOGY.md §1.2.2 specifies (per-slot rolling 7-day trailing minimum) against the 42 coarse-screen-flagged households. Result: **only 1 of the 9 households visually rated "clean" in the pre-mortem check passed, while 2 of the 6 rated "not clean" passed** — close to inverted agreement with direct visual inspection, not noise. Diagnosed on MAC004863 (visually one of the cleanest signatures): plotted raw / baseload-proxy / residual side by side (`data/intermediate/diagnostic_MAC004863.png`). The baseload-proxy panel is visibly a near-exact copy of the household's own overnight charge block, not background noise — confirms the predicted failure mode exactly: this household charges at a near-constant ~4.8kW every night, so the same-slot 7-day trailing minimum converges to the charge level itself, leaving almost no residual.

**Fix implemented:** `_baseload_proxy_daytime` (new function in `src/signature_detector.py`) draws the baseline from a 10:00–16:00 daytime reference window instead of the same overnight slot being tested — structurally immune to contamination by the household's own heater signal, since that window doesn't overlap the charge-detection window (23:00–07:00) or the boost-detection window (16:00–20:00, METHODOLOGY.md §1.3). This is a deviation from METHODOLOGY.md §1.2.2's literal text, made because the literal version was tested against real data and demonstrably failed, not preferred on aesthetic grounds. `_baseload_proxy` (original) kept in the file for reference, not deleted, per §17 (never overwrite a working/frozen approach without keeping the prior version visible).

**Re-run with the fix:** 21/42 households now qualify (up from 7/42). Visual agreement improved but is still far from clean: 2/9 visually-clean pass, 3/6 visually-not-clean pass. Investigated the most surprising flip (MAC003218, passed under v1, visually clean, fails under v2) rather than accepting the number and moving on: `data/intermediate/diagnostic_MAC003218_v2.png` shows the v2 baseload proxy is behaving correctly (stays low, ~0.2–0.5kW, genuinely off the household's own signal) — but MAC003218's overnight charge block runs **10–13kW**, far above the 1.8–3.2kW charge band (METHODOLOGY.md's own illustrative example, flagged UNTESTED in `config/phase1_config.py` from the start). This isn't a baseline-estimation bug — it's a second, independent problem: **the fixed charge band is too narrow for the real range of overnight demand in this population.** Checked the distribution across all 42 coarse-screen-flagged households: overnight mean kW ranges from 1.51 to 9.38 (mean 2.26, median 1.93) — the band captures the bulk of the distribution but excludes real outliers on the high end, plausibly multi-heater households or larger systems, not obviously non-storage-heater loads.

**Not yet resolved — flagged for the next step rather than patched unilaterally a second time in the same pass (per §2.8: don't keep re-tuning until the answer looks right without stopping to think).** Two known, well-diagnosed problems now stand between the current 21/42 figure and a number worth reporting as Phase 1's finding: (1) the charge-band upper bound may need to be loosened, made per-household-adaptive, or dropped in favour of a lower-bound-only test; (2) visual agreement, even after the baseline fix, remains poor enough that the visual pre-mortem sample itself, the charge-band definition, or both need re-examination before either is treated as a check on the other.

## 2026-08-31 — Charge band fixed per user's domain knowledge; steadiness gap surfaces and is falsified

User's estimate: a typical UK 2-bed property runs ~5 storage heaters. Checked against real market data (Eco Experts, EDF, storageheaters.com, MPC Energy, MoneySavingExpert forum): common unit ratings run ~0.85-3.4kW, with 1.7kW/2.55kW/3.4kW being standard sizes. Five units at 1.7-2.55kW each puts simultaneous household draw at ~8.5-13kW — matches MAC003218's observed 10-13kW block almost exactly. Confirms the original 3.2kW upper cap assumed one heater, not a household.

**Fix:** dropped the upper bound entirely (`charge_band_high_kw` deprecated in `config/phase1_config.py`, kept for traceability, not deleted). Re-ran: **42/42 households now qualify — zero discrimination.** This is itself informative, not a result to accept: removing the cap also silently removed the only thing checking for a *steady* plateau, so any sustained elevated reading now passes regardless of shape.

**Attempted second fix:** added an explicit steadiness check — (max-min)/mean within a candidate charge run must be ≤ 0.4 (guessed threshold, flagged untested). Re-ran: 16/42 qualify, but agreement with the visual pre-mortem sample got *worse* (1/9 clean pass), and MAC003218 — independently confirmed via diagnostic plot to be a genuine, strong household signature — dropped to a 0.0 charge-night fraction.

**Falsified rather than accepted:** measured the actual relative swing within confirmed-good nights for MAC004863 and MAC003218 directly (not guessed): median 0.52 and 0.79 respectively, individual nights up to 1.11. The 0.4 threshold was wrong by a wide margin — real storage-heater charging is genuinely noisy within a night (plausibly from multiple heaters cycling independently), and the "steady rectangular block" read from the zoomed-out multi-day pre-mortem chart doesn't hold at half-hour resolution. This also means the 15-household visual pre-mortem sample is not a reliable calibration target at this resolution — three tuning rounds against it produced three different failure modes, which is the pattern §2.8 warns against, not genuine convergence.

**Decision point put to the user rather than continuing to guess a fourth threshold.** Chose: get a real validation set (UK-DALE) before refining further.

## 2026-08-31 — Seasonal check (user's idea) leads to the best discriminator found tonight

User's insight: storage heaters have a hard physical tell that a per-night residual test doesn't exploit — they should show a seasonal on/off pattern (temperature-driven), or in the "always left on" case, a flat high level across seasons that is itself the clearest possible illustration of PROJECT.md's overcharging thesis. Proposed a 3-feature matrix: (1) max overnight kW in January (physical floor), (2) January/July overnight-mean ratio ("R_seasonal", seasonal check), (3) night energy as a share of total January energy ("S_night", diurnal concentration).

**Checked computationally against the 42 coarse-screen-flagged households rather than accepted on the reasoning alone** (per this session's repeated lesson: physically-reasonable thresholds have not survived contact with real data tonight).

- **Feature 3 (S_night) is the strongest discriminator found in this entire session.** All 9 visually-clean households (pre-mortem sample): 0.71–0.85. All 6 visually-not-clean households: 0.36–0.45. Zero overlap. Cleaner separation than any version of the residual/steadiness detector produced.
- **Feature 2 (R_seasonal) as originally specified has a division bug and a conceptual gap.** MAC005263's ratio computed to ~3,041,278 — not an outlier signal, a `÷≈0` artifact: July sums to exactly 0.0 kWh across 1,488 valid readings, more likely a vacancy/meter-fault/dropout than genuine "off for summer" and needs flagging as a data-quality case, not fed through the ratio. Separately: MAC004863 (independently diagnostic-confirmed as a genuine strong signature earlier this session) has R_seasonal ≈ 1.03 — January 4.506kW, July 4.365kW, essentially no seasonal difference. A strict R_seasonal≥1.8 gate would have wrongly excluded it. This matches the user's own "leave it on at all times" observation exactly — treated as a real household sub-type (year-round chargers), not noise to threshold away.
- **Feature 1 (max overnight kW, Jan) adds no discrimination on this population** — all 42 already clear a 2.0kW floor, unsurprising since the coarse screen already selected for elevated overnight demand. Likely more useful applied to the full 4,411-household population before the coarse screen, not after.

**Revised design, replacing the residual/steadiness detector line of work:** S_night as the primary confirming signal (threshold to be set in the clear 0.45–0.71 gap, e.g. ~0.55–0.60), R_seasonal used to classify confirmed households into seasonal-responsive vs. year-round types rather than as a pass/fail gate, with an explicit floor on the denominator (or absolute-zero-month flag) before computing any ratio, and Feature 1 kept as a sanity floor rather than a discriminator.

- Simple constant-rate decay model: `predicted_runout_hour = 07:00 + night_kwh / release_rate_kw`. **Cross-tabulation still runs backwards after recalibration.** Nights where the model predicts exhaustion by 20:00: 50.0% show boost. Nights where it predicts NOT exhausted: 64.1% show boost — higher, not lower. This survived a proper recalibration, which rules out "wrong constant" as the explanation.

**Conclusion, reported honestly per METHODOLOGY.md's own instruction ("if exhaustion shows up randomly... the model doesn't have a story, and shouldn't claim one"):** the population-level cold/mild association is real, but this more specific test — does the decay model's predicted exhaustion *time* predict boost occurrence — does not hold up, even properly calibrated. The boost detector's 56% flag rate is consistent with this: too high to plausibly be a rare, distinct backup-heating signature, more consistent with catching ordinary evening appliance use.

**Not pursued further this session** (per §2.8 — a third guessed parameter to force the cross-tab to agree would be exactly the "adjust until it looks right" pattern this project explicitly rules out). ## 2026-09-02 — Humidity/comfort claim (METHODOLOGY.md §2.3): checked against real standards, resolved

**Original claim checked directly against ISO 7730 (2005 and 2025 editions, consistent wording in both):** the standard's own precise relationship is "a 10% higher relative humidity and a 0.3°C higher operative temperature are perceived as being warmer in equal measure." Worked the math: the claimed "18°C feels like 21°C" (a 3.0°C claim) would require a 100-percentage-point RH swing to support — physically impossible, since RH only ranges 0–100%. A realistic dehumidifier-achievable swing (70%→40% RH, 30pp) supports only ~0.9°C. ISO 7730 also states directly that "in moderate environments the air humidity has only a modest impact on thermal sensation" — the standard's own guidance is to disregard this effect near comfort temperatures, not build a headline claim on it.

**User supplied a "corrected" pitch citing CBE's Thermal Comfort Tool and ASHRAE 55**, reframed around dampness/mould rather than a temperature-equivalence number — but the reframed pitch's closing clause ("keeps 19–20°C feeling completely comfortable without needing to overheat to 22°C+") reintroduced essentially the same ~2–3°C equivalence claim in different numbers. Checked rather than accepted on the strength of the better citations: found an independent source using the more sophisticated two-node SET/ET* model (not just ISO 7730's simplified PMV rule of thumb) reaching the same conclusion — "humidity has only a small effect on thermal comfort" across a wide 20–55% RH range near the comfort zone. Two different models, two different standards bodies, same answer: no realistic indoor humidity swing supports a multi-degree comfort-equivalence claim.

**Also caught a citation-scope mismatch:** ASHRAE 55 explicitly disclaims mould coverage — "ASHRAE Standard 55 is strictly limited to thermal comfort considerations, so mould issues... are not accommodated in the ASHRAE 55 thermal comfort recommendations." Citing ASHRAE 55 for the mould/dampness claim specifically would be citing the wrong standard for that half of the pitch, even though it's the right standard for the comfort half.

**Resolved, agreed with the user:** keep the dampness/mould framing (well-supported, multiple independent sources confirm 40–60% RH as the right range for both comfort and mould prevention) but drop the specific temperature-equivalence number entirely. Final grounded copy direction: *"keeping humidity between 40–60% stops that damp, clammy feeling and helps prevent mould — you shouldn't need to push the heating past 20°C for comfort once the air's drier."* No fabricated degree-equivalence, no ASHRAE-55-for-mould mismatch, keeps the genuinely solid claims.

## 2026-09-02 — Known limitation: household-level modelling, not per-heater

Flagged by Andy: AutoMagic (and the underlying calibration data) models the whole household, not individual storage heaters. The Low Carbon London smart meter data the calibration is built from measures total draw at the meter -- it cannot distinguish which heater in a home used how much. The app mirrors this: one postcode, one dial-max, one tariff, one nightly recommendation per household, on the assumption of a single heater or heaters moving together.

This is a real gap where a household has several storage heaters run differently by room -- e.g. a tenant may reasonably want the bedroom heater very low or off while running the lounge heater harder. The app's input-dial advice (when/how much to charge) is probably fine as a single household-level number, since that's driven by weather and price, not room-by-room need. The output dial (how fast to release stored heat) is where the gap matters most, and the app already deliberately stays silent on that as a per-room "comfort control" rather than pretending to have a forecast for it -- so the design has implicitly fenced off the part it can't honestly model, though the UI doesn't say this explicitly anywhere yet.

Not planned to fix now: doing so would need per-circuit or per-appliance monitoring data that doesn't exist anywhere in this project's evidence base (LCL is whole-household only). Logged as a known limitation, not a bug.

**General advice (outside the app, not modelled):** for a room that's rarely occupied or doesn't need overnight heat (e.g. a spare bedroom), the standard practical guidance is to turn that room's storage heater down very low or off and use an electric blanket instead for occupied-night comfort -- cheaper and more targeted than heating an unused room's thermal mass all night. Worth a mention in tenant-facing guidance material at some point, but it's general good-practice advice, not something AutoMagic itself calculates or personalises per room.

## 2026-09-03 — Real limitation confirmed: LCL_2013.csv predates both the post-2021 energy crisis and Awaab's Law's excess-cold provisions

Andy raised a concern about using LCL_2013.csv as the calibration source: household heating behaviour in 2013 may not represent 2026 conditions, specifically citing fuel poverty and Awaab's Law. Checked both rather than taking on faith -- both hold up, and the second is a genuinely significant, timely finding worth flagging on its own.

**Fuel poverty has risen substantially since 2013, driven by the 2021+ energy crisis.** House of Commons Library briefing (April 2025): under the 10% income-based definition, government estimates ~9.0 million UK households as fuel poor -- "almost double its level in 2021." Official England definition (LILEE-style) put it at ~11% of households in 2024. Precise 2013 figures weren't in the source checked, but the qualitative point is well supported: 2013 predates the 2021-23 gas price shock entirely, so a 2013 household's overnight storage-heater usage reflects a meaningfully less cost-constrained decision than a 2026 household's does. This is a real reason a 2013-calibrated Target Charge Index could systematically misjudge what a real 2026 fuel-poor tenant would actually do at a given temperature.

**Awaab's Law Phase 2 -- arrives 30 November 2026, under three months away -- adds "excess cold" as a legally enforceable hazard category for social landlords for the first time.** This did not exist in any form in 2013 (Awaab Ishak died in 2020; the law followed from that case). From 30 November 2026, social landlords must "identify, investigate and resolve" excess-cold hazards within statutory timeframes, with an auditable communication trail -- explicitly naming "properties with inadequate heating, poor insulation or defective heating systems," and flagging "older stock, hard-to-treat homes and properties affected by fuel poverty" as the properties most likely to be in scope. This describes this project's target housing stock almost exactly. Two implications: (1) it's a second, independent reason 2013-era data may not represent today's regulatory or behavioural reality (there was no legal cold-hazard deadline pressuring landlords or shaping tenant expectations in 2013), and (2) separately from the data-quality question, this is a real, near-term reason a housing association might want a tool like NightDial *now* -- a compliance angle worth remembering when this project is discussed with HAs, not just a technical footnote.

**Net effect on the LCL_2013.csv pipeline (still deferred, not started):** proceed with it as planned when it's picked up -- Andy's own words, "it's the best data we have" -- but whatever calibration comes out of it needs an explicit, permanent caveat attached (in the app footnote and in any HA-facing material) noting it predates both the 2021+ energy crisis and Awaab's Law, so it may understate real cold-related risk in a way that matters for excess-cold compliance specifically. Worth designing the pipeline's own output/report to state this caveat by default, not as an afterthought.

## 2026-09-07 — Checked: is storage heating actually greener than gas, or is it "gas by another route"?

Andy raised a real point the project hadn't checked: gas central heating is the cheapest option for a tenant but not the best for Net Zero, and storage heaters charge overnight on a grid that leans on gas to fill the gap when wind is low -- so switching a tenant from gas to an unmanaged storage heater might not be the carbon win it's assumed to be. Checked with real, current UK conversion factors rather than assuming either direction.

**The numbers, using the 2026 DESNZ/DEFRA government conversion factors (checked directly):** natural gas, 0.18296 kgCO2e/kWh (gross CV). Grid electricity (annual average), 0.177 kgCO2e/kWh. A modern condensing gas boiler runs at roughly 90% efficiency; a resistive storage heater converts electricity to heat at effectively 100%. Per kWh of *heat delivered*: gas boiler ~203 gCO2e; resistive electric storage heater ~177 gCO2e (using the grid annual average) -- so on a straight annual-average basis, a storage heater is already somewhat greener than gas, not "gas by another route." A heat pump at a realistic SCOP of 3 delivers the same heat for ~59 gCO2e -- less than a third of gas's figure.

**But the annual average hides real volatility, and the volatility is worst exactly when storage heaters work hardest.** A live UK grid-carbon tracker (purelyenergy.co.uk, checked directly) reports a 2026-year-to-date range of 20-311 gCO2/kWh, against a ~141 gCO2/kWh average on that source (a different, more current methodology than DEFRA's trailing annual factor, but directionally consistent). Separately (mygridgb.co.uk, checked directly): overnight hours are typically *lower* carbon than daytime on a typical night (midnight-6am running ~20% below the daily average), because overall demand drops and gas generation scales down with it -- not because cleaner sources take over. That's the normal-night case, and it's good news for storage heating generally.

**The bad-night case is the one that matters for this project's own numbers.** Storage heaters do 52.9% of their year's charging in Nov-Feb and 44.5% in just Jan/Feb/Mar (2026-09-02 finding, already logged). Those are also the conditions most associated with a UK "wind drought" -- cold, still, high-pressure winter nights, precisely when wind output can collapse and gas has to fill nearly the whole gap. On a night like that, grid carbon intensity plausibly sits toward the top of the 20-311 g/kWh range recorded this year -- above gas's ~203 g/kWh-heat figure, meaning a storage heater charging through that specific night could be *dirtier* than the gas boiler it replaced, not greener. **This is not confirmed with real minute-by-minute data matched to actual charging windows -- nobody has run that comparison for this project's own household-nights yet.** Stated as a plausible, sourced risk, not a settled finding either way.

**Why a heat pump is structurally immune to this problem in a way resistive heating never can be.** Even on the single dirtiest hour recorded on the live tracker this year (311 gCO2/kWh), a heat pump at SCOP 3 delivers heat at ~104 gCO2e -- still roughly half of gas's ~203 g/kWh-heat figure, on the worst grid hour of the year. Resistive heating (storage or point) has no such margin: its carbon intensity *is* the grid's, one-to-one, with no efficiency multiplier to absorb a bad night. This is an independent, non-cost argument for the same conclusion the cost numbers already pointed to: a heat pump is the only technology in this comparison that's robust to real-world grid variability, not just cheaper to run under average conditions.

**On Andy's wider point (paying for gas's real cost, or paying for tenant warmth directly):** sound, standard economic reasoning for this class of problem, not checked against a specific UK policy proposal this session -- a carbon price on gas would fix the market signal but falls hardest on people who can least afford it unless paired with a compensating transfer (a carbon-price-and-dividend structure, or a direct targeted warmth subsidy, are the usual ways economists reconcile decarbonisation with fuel poverty). Flagged as a sound framing, not independently sourced to a live UK proposal this session.

## 2026-09-07 — Documented and calculated: does a real cold, low-wind night actually push storage-heater charging above gas's carbon intensity?

**The single biggest, most quantifiable driver: the electricity-to-gas price ratio, and it is a policy design choice, not a natural market fact.** Sourced directly (Nesta): UK electricity costs roughly 4.3x gas per kWh as of April-June 2026 (24.67p vs 5.74p in Nesta's figures; close to but not identical to the Ecotricity-specific 29.13p/7.51p already logged — different supplier averages, same order of magnitude). Critically: only ~44% of the electricity price is actual commodity/fuel cost, versus ~52% for gas — the rest is network, policy and environmental-scheme costs, loaded disproportionately onto electricity bills rather than gas. This directly explains why this session's own breakeven-SCOP calculation (3.49 on a standard tariff) came out so demanding: it isn't that heat pumps are inefficient, it's that UK policy has structurally inflated the price of the fuel they run on relative to the fuel they compete against. A "rebalancing" of these levies (proposed by multiple bodies, including the MCS Foundation and Nesta, not yet implemented) would lower that breakeven SCOP directly.

**A real installer capacity shortage, not a perception problem.** Sourced (Nesta): ~3,000 qualified heat pump engineers currently active in the UK; the government's own 600,000-installations-a-year target implies needing ~27,000 by 2028 and ~62,000 by 2035 — a roughly nine-fold increase in six years, needing 5,000-7,000 newly trained installers a year. Only ~23% of heating trades professionals are currently fully trained on ASHP installation (housingevidence.ac.uk). Existing gas engineers have little financial incentive to retrain (no wage premium for heat pump work, retraining costs up to £2,000).

**Practical and tenure barriers specific to exactly this project's population (flats), not generic.** Sourced: almost every leasehold flat needs freeholder consent for an external unit (consent fees £200-500, surveys £300-800, 8-16 week timelines even when cooperative); many flats lack space for a hot water cylinder (200-300L) since they're built around combi boilers; communal/district heating systems block individual retrofit entirely; MCS 020 noise-distance rules bind harder in dense terraces and blocks. One blog source estimated ~70% of UK flats are retrofittable "given the right circumstances," 30% blocked by lease terms or building constraints — flagged as an indicative, not rigorously sourced, figure (a property-advice blog, not a primary study). These compound, rather than duplicate, the "no existing wet system" capex issue already logged — a flat can clear the wet-system hurdle and still be blocked by freeholder consent or lack of cylinder space.

**Consumer perception and status-quo bias, real but harder to quantify.** 74% of English and Welsh households are on mains gas (housingevidence.ac.uk) — an enormous embedded incumbent base, with gas infrastructure subsidy history dating to the 1940s. Multiple sources note many gas-heating occupants report high satisfaction with their current system and resist switching to an alternative perceived (correctly or not) as unproven, noisy, or ineffective in cold weather. Policy instability (repeatedly shifted government schemes/targets) was also named as discouraging both household and installer investment.

**How this bears on the project's own findings.** None of this contradicts the previous entry's numbers — it explains WHY the breakeven point sits where it does (policy-driven price ratio), why "just install a heat pump" is harder in practice for this specific flat-heavy population than the general national conversation assumes (tenure/consent/space barriers layered on top of the wet-system and BUS-exclusion issues already logged), and why the capex/funding blocker this project keeps landing on is itself downstream of a set of deliberate, named, and in-principle-reversible policy choices rather than an unavoidable fact of physics or economics — carbon and (tariff-conditional) running cost both worked in heat pumps' favour; adoption is being held back by policy design, installer capacity, and tenure structure, not by the technology failing on its own terms.

## 2026-09-07 — Would solar and battery close the heat pump breakeven gap? And does council/HA freehold ownership solve the tenure barrier?

**Solar: real but thin, and hit by the same negative correlation that already undermined solar-for-storage-heaters.** UK domestic solar output (PVGIS-based, typical south-facing array): 29 kWh/kW in December, 33 in January, 49 in February, versus 117-119 kWh/kW in May/June/July — December delivers roughly a quarter of June's output. A typical 4kW array therefore generates ~3.7-4.8 kWh/day averaged across Dec-Feb. Real heat pump winter demand (DESNZ Electrification of Heat trial): 25-40 kWh/day in Dec-Feb, January averaging 28 kWh/day, versus just 3-8 kWh/day in summer (hot water only). That puts solar's realistic winter coverage at roughly 12-18% of heat pump electricity use — close to, but short of, the ~20% free-electricity threshold that would bring the real field SCOP (2.78) to parity with gas on a standard tariff (see the breakeven-SCOP entry logged 2026-09-07). The gap that actually matters: the coldest, stillest, highest-demand nights (the same nights driving the 35%-of-nights-beat-gas carbon finding) are typically preceded by the greyest, lowest-solar days — the identical negative correlation already flagged for storage heaters, just less severe because heat pumps need less electricity per unit of heat to start with.

**Battery: shifts a thin pool, doesn't create a bigger one.** Typical UK domestic batteries run 5-10kWh (£3,500-8,500 installed) — roughly a quarter to a third of one day's winter heat pump demand. A battery can capture more of the already-thin daytime solar trickle for evening use, and can in principle store cheap off-peak (E7/Cosy) electricity for use in a tariff's priciest window (Cosy Octopus peak: 16:00-19:00, 51.68p/kWh) — but the core breakeven calculation already assumes running the heat pump preferentially during the off-peak window itself, which captures most of that value already, for zero extra capex. Solar+battery together (roughly £8,500-£20,000+ installed) add meaningful capex on top of a heat pump whose funding gap (BUS excludes social housing entirely, logged 2026-09-07) is already the single largest blocker found. **Conclusion: a real but second-order lever, not a fix — the tariff switch alone (E7/Cosy vs standard) gets the same real households to full parity with gas for zero extra hardware, which does more work for less money than adding solar/battery capex.** Flagged as a reasoned estimate from cited external generation/demand figures, not a full per-household recomputation against the project's own weather-matched data — a natural next step if this becomes decision-relevant.

**Council/HA freehold ownership: a real structural advantage, confirmed against DHLUC's own mixed-tenure study — but it clears only one of the four named barriers.** The tenure/consent barrier already logged (almost every leasehold flat needs an external freeholder's consent, £200-500 fees, £300-800 surveys, 8-16 week waits) assumes landlord and freeholder are different parties. For most council/HA stock, they're the same party: DHLUC's "Understanding mixed tenure in English social housing" study (fetched directly) puts the mean social-tenant ratio across mixed-tenure-eligible developments at 80%, but the **median at 97%** — most social blocks are overwhelmingly landlord-owned, not fragmented across many private owners. Purpose-built flats specifically sit at a 91% median social ratio. For that majority of stock, the freeholder-consent bottleneck that blocks a private leaseholder mostly doesn't exist: the landlord doesn't need to ask itself for permission. Three real caveats: (1) not universal — converted flats (50% median social ratio) and inner/outer London stock (76-79% median) are genuinely mixed via Right to Buy, and the same DHLUC report flags that whole-building works (their example: external wall insulation; the same logic applies to communal-system or whole-block heat pump retrofit) hit real consent friction exactly where private leaseholders sit alongside landlord-owned units; (2) removing the tenure barrier does nothing for the other three found this session — physical space/communal heating systems (orthogonal, and common in exactly this stock), the installer shortage, or the funding exclusion (BUS excludes social housing regardless of tenure structure) — which is currently doing the most damage of the four; (3) permitted-development/planning noise-distance rules (MCS 020) bind on a landlord-owned block exactly as they would on anyone else's. **Conclusion: a genuine, evidence-backed insight worth carrying forward — councils/HAs are structurally better placed than the private-leasehold-flat case the barrier research focused on, for the specific reason of freeholder/landlord being the same party — but it resolves one barrier out of four, and not the one (funding) currently binding hardest.**

## 2026-09-07 — Can China commoditize heat pumps like it did solar? And is solar a much better match for heat pumps in summer than winter?

**China and heat pump cost: already happening for the hardware, structurally capped for the rest.** UKERC's evidence review of UK installed heat pump costs (peer literature review) breaks a UK installation down as: equipment ~60% of total cost, non-equipment (design, labour, commissioning, distribution) ~40%; within equipment, the heat pump unit itself and ancillary equipment (cylinder, radiators, pipework) are roughly evenly split — putting the unit alone at roughly 30% of total installed cost, consistent with a separate retailer source's own "30-40%" estimate. The same UKERC review found rest-of-world ASHP costs fell 22% (2015-19 vs 2020-29) against only 6% in the UK, attributing the successful cases (Switzerland, Netherlands) specifically to "supply chain competition and component importing" — explicitly citing cheaper Asian-made compressors as the mechanism, and naming UK policy support as too weak to have captured the same gain. This is already visible at retail: Midea (Chinese manufacturer) 8kW units run £2,544-3,054 supply-only in the UK today, £750-1,250 cheaper than premium European brands (Vaillant, Viessmann) for comparable output. So the Chinese-commoditization effect Andy is asking about is real and already underway for the box itself — not a hypothetical.

**But it caps out well short of solar-style commoditization, because the product is structurally different.** A solar panel is nearly the entire deliverable, and fitting it is comparatively simple, standardised labour — which is why Chinese scale (China holds >80% of global solar manufacturing capacity, panel prices down ~90% since 2010) could commoditize almost the whole cost. A heat pump is a component inside a bespoke wet-heating-system retrofit: even a hypothetical free heat pump unit would still leave the ~40% non-equipment share (site survey, system design, commissioning) and much of the remaining equipment share (cylinder, radiator upgrades, new pipework — often needed converting from storage heaters, per the wet-system issue already logged) as UK-labour-bound costs that no factory in Guangdong ships over. That non-equipment/ancillary share is gated by the same installer shortage already logged (~3,000 active UK engineers vs ~27,000/62,000 needed) — cheap Chinese hardware doesn't create more UK installers. **Verdict: partial yes, already real for roughly a third of the cost, structurally incomplete for the rest — installation capacity, not manufacturing cost, is the more stubborn half of the UK heat pump cost problem.**

**Real-time proof of the same dynamic with near-identical Chinese cooling technology.** The 2026 European heatwave (150m+ people affected, 1,300+ heat-related deaths) drove a genuine, large-scale surge in Chinese air conditioner imports — EU imports hit $3.76bn Jan-May 2026, up 43% year-on-year — while, unlike solar panels and EVs, the EU has not moved to impose anti-dumping tariffs, explicitly because ordinary Europeans need the cheap supply now (commentary framed this as "the air conditioner paradox"). Chinese manufacturers were reported meeting European standards (French refrigerant limits, German noise rules, Swiss efficiency requirements) at substantially lower prices, at real volume, right now. Air-to-air heat pumps use the same core refrigerant-cycle hardware as these air conditioners (already logged as reversible and cooling-capable, unlike the air-to-water units this project has otherwise assumed) — so this is direct, current evidence that Chinese manufacturing can and does hit UK/EU-equivalent standards on this exact class of hardware at scale.

**Solar and heat pumps: a much better match in summer than winter, and it's the same physics running in the opposite direction.** Winter heating demand and winter solar generation are anti-correlated (cold, still, high-demand nights follow the greyest, lowest-solar days — logged 2026-09-07). Summer cooling demand and summer solar generation are the mirror image: both are driven by the same thing — high sun angle and long daylight hours — so a heat pump running in cooling mode on a hot afternoon is drawing its heaviest load at exactly the moment solar output peaks, with no storage needed to bridge the gap. This is a real, structural asymmetry worth stating plainly: solar's poor fit for heating and its strong fit for cooling aren't two separate facts, they're the same mechanism (solar tracks the sun; the two demands relate to the sun in opposite directions) pointing different ways by season. **Caveat already logged and still binding:** this strengthens the technical case for air-to-air heat pumps in this housing stock (Awaab's Law Phase 2 overheating angle, logged 2026-09-07) but doesn't touch the funding barrier — air-to-air is BUS-excluded for social housing exactly like every other heat pump type, so the summer-solar argument is a genuine technical point in air-to-air's favour, not yet a financeable one for this project's population.

## 2026-09-07 — Standardized social housing stock and standardized-fitment heat pumps: both real, and they attack exactly the cost/installer problem hardware commoditization can't touch

**"Less bespoke" social housing stock is real, at real scale, and already the basis of a live UK programme — not just a hunch.** Roughly 1 million UK dwellings were built using non-traditional/system-built methods between 1919 and the 1970s, overwhelmingly for local authorities, and some individual systems are huge (Wimpey No-fines ~300,000 units, Easiform ~90,000). This is precisely the population a real, current initiative already targets: an "archetype-led packaged retrofit" approach aimed at ~200k non-traditional social housing archetype homes (1920s-1970s) for standardized heat pump solutions, explicitly because measured data shows homes of the *same* archetype can vary by over 20% in heat pump efficiency purely from inconsistent installation — i.e., standardization is being pursued specifically to close a real, measured variability gap, not a hypothetical one. Caveat: BRE lists 500+ distinct non-traditional systems nationally, so this is "large repeated types," not one universal design — realistically a modest number of kit variants covering the largest archetypes, not a single standard fit for all social housing. And Right to Buy has moved a meaningful share of this exact stock into private ownership since the 1980s, intersecting with (but not contradicting) the mixed-tenure finding already logged.

**Standard single-connection-point units already exist: they're called monobloc heat pumps, and it's the same lever Switzerland/NL already used.** A monobloc unit is fully self-contained — refrigerant circuit, compressor, and hydronics sealed in one outdoor box — connecting to the house via water flow/return pipes and an electrical supply only. Because the refrigerant circuit is hermetically sealed at the factory, monobloc installation does **not** require F-Gas certification on site (unlike split systems) — directly relevant to the installer-shortage barrier already logged (~3,000 active UK engineers vs ~27,000/62,000 needed): monobloc adoption widens the pool of who's legally allowed to do the water/electrical side of the job, without needing more specialist refrigerant-handling engineers. This is the same "component importing" mechanism the UKERC report credited for Switzerland and the Netherlands' faster cost falls (logged 2026-09-07) — sealed, factory-standardized units reduce what has to be built bespoke on site.

**How this fits the previous entry's cost split, and its real limits.** The China/commoditization analysis (logged 2026-09-07) found manufacturing scale can only realistically compress the ~30-40% hardware share of installed cost, capped by the ~60-70% design/survey/installation-labour share being inherently site-specific. Standardized building archetypes plus standardized (monobloc) units are a plausible, real lever specifically against that harder-to-shift labour/design half — turning a bespoke site survey into a known, repeatable spec for a given archetype, and turning on-site refrigerant work into a factory-sealed non-issue. The two ideas compound rather than duplicate: cheaper Chinese hardware attacks one cost pile, standardized fitment attacks the other. Scale of the problem this would need to solve: UK government's own target is 600,000 heat pump installations/year by 2028; actual 2023 MCS-certified installations were 36,799 (up 20% YoY, "still far below what's needed") — standardization/packaging is aimed at closing exactly that rollout-speed gap, not just a cost gap.

**Honest caveat from real UK delivery data, not just design promise.** Energiesprong UK's own performance review of 69 standardized/prefabricated retrofit homes found real heat pump SCOP averaging 2.44 against a 2.6 design target (adding ~100 kWh/year electricity demand versus plan), residents consuming ~30% more electricity than modelled, and homes run 2°C warmer than the design spec (a comfort take-back effect) — while still achieving 70%+ energy reduction versus typical UK dwellings. Standardization measurably helps, and is already a real UK strategy at real scale, but real installations still under-deliver against their own design targets, for the same reasons (real-world commissioning quality, occupant behaviour) already flagged elsewhere in this project's evidence discipline — a reason to keep using real, delivered field data rather than design-target figures when this ever needs a hard number for this project's own households.

## 2026-09-08 — Attempted demand-weighted carbon recomputation: hit a real data-availability wall, reporting honestly rather than forcing an answer

**What was attempted.** Following through on the flagged next step from 2026-09-07 (the naive average of 23 hand-picked cold/still nights may overstate storage heating's carbon advantage, since it doesn't weight by how much electricity each household actually draws on each night), tried to compute a true demand-weighted mean carbon intensity: real per-night kWh from all 40 households across the full 2013 calibration year (`phase1_household_nights.parquet`, 14,558 household-nights, 364 distinct dates), weighted by that night's real grid carbon intensity.

**The hard constraint found: real matching-date carbon intensity data does not exist for 2013.** Checked directly against the live Carbon Intensity API (api.carbonintensity.org.uk) rather than assumed: a request for 2013-01-15/16 returns `null` (no data), while an identical-shaped request for 2018-06-01/02 returns full real half-hourly data. The API's actual/historical carbon intensity coverage starts 1 May 2018 — it does not, and cannot, cover the 2013 household calibration dataset's dates. (NESO separately publishes a historic generation-mix dataset from 2009, but it's fuel-mix by type, not a ready carbon-intensity-per-kWh figure, would need emissions-factor conversion, and its bulk-download endpoint is blocked from this sandbox's network policy — not pursued further as a workaround given the scale of the conversion work needed for what would still be a fuel-mix estimate, not a direct measurement.)

**The fallback attempted, and why it's not trustworthy enough to publish.** Built a proxy: fit a linear regression of the 23 real sample nights' mean carbon intensity against that date's real London temperature and wind (Open-Meteo), then applied it to 2013's real daily temperature/wind to estimate a carbon intensity for every 2013 household-night, and weighted by real kWh. Result looked clean (78 gCO2/kWh demand-weighted average, both technologies) but is not reliable: **R² = 0.183** — local temperature and wind explain under a fifth of the real variation in grid carbon intensity (residual std ~58 gCO2/kWh), because intensity is actually driven by GB-wide demand, wind generation, and plant availability, not one city's local weather. Worse, the regression was fit only on the 23 nights' narrow calibration range (-2.2°C to 5.4°C, 2.3-9.7 km/h wind) — deliberately selected as the *coldest/stillest* nights of 2024-25, not a representative sample — while 74% of the real 2013 households' total heating kWh occurs above 10°C, up to 23.8°C. Extrapolating a weak model built on an extreme, narrow slice out across a whole year is not a defensible basis for a published figure, and doing so silently erased the very tail-risk finding it was meant to check: the extrapolated full-year result showed 0% of kWh on nights exceeding the gas benchmark, against the original honest 35%-of-nights finding from the real sample itself.

**Restricting the estimate to only the nights the model can honestly speak to** (2013 dates whose real temperature+wind fall inside the 23-sample's calibrated range) narrows the sample to 20 distinct 2013 dates, covering just 9.0% of the fleet's total annual kWh (800 of 14,558 household-nights). Within that narrow, honest range: demand-weighted mean intensity ≈143.5 gCO2/kWh (still below the 203 g/kWh gas benchmark on average, 0% of this narrow subset's kWh exceeding it) — but this is a low-confidence, 9%-of-demand estimate, not the full-year answer sought, and its 0% exceedance rate (versus the original spot check's real 35%) is itself evidence that the proxy is too smoothed to trust for tail-risk claims.

**Honest conclusion: this specific recomputation isn't achievable with the data actually available, not a matter of more effort.** The 2013 household dataset (the well-known open London smart-meter dataset used throughout this project, chosen because it's one of the only genuinely open, real household-level datasets at this granularity) predates all real UK carbon-intensity measurement by five years. There is no way to honestly demand-weight 2013 consumption against 2013 grid carbon data, because the latter was never measured. The original 23-real-night spot check (2024-25, hand-picked coldest/stillest nights, 35% exceeding gas, mean 163.5 g/kWh) remains the best real evidence this project has for the tail-risk carbon claim — real dates, real measured grid data, explicitly selected as the adversarial case Post 3 needed to check. It should be reported and used as exactly that (a real, worst-case-focused spot check), not blended with the 2013 consumption data via an unreliable weather proxy to manufacture a false precision full-year number.

**What would actually fix this, for a future session:** either (a) find or build a genuinely comparable real household consumption dataset from 2018 onward (so the real Carbon Intensity API can be matched date-for-date, no proxy needed), or (b) deliberately fetch a broader, non-cherry-picked real sample of nights across a full recent winter (covering the full range of temperatures storage heaters actually operate in, not just the extremes) to get a properly demand-weighted answer for *today's* grid — accepting that it describes a hypothetical "if these real households' known usage *pattern* by temperature occurred on today's grid" rather than literal 2013 emissions, consistent with how this project already treats 2013 usage against 2026 prices.

## 2026-09-08 — Route B executed: a real, demand-weighted carbon comparison, no proxy or extrapolation needed

**Method.** Fetched 31 new real nights directly from the Carbon Intensity API, deliberately stratified across the real kWh-weighted temperature distribution of all 40 households' 2013 heat demand (not hand-picked extremes) — spanning -0.7°C to 19.1°C, with a spread of wind conditions in each 2°C band, drawn from real dates across all of calendar 2025 (not just winter). Combined with the original 23 cold/still-night sample for 54 real nights total, covering (with the small-tail fallback noted below) the full real temperature range the household dataset actually operates in. Built an empirical lookup (real observed mean, min, max intensity per 2°C temperature bin) rather than a regression — deliberately avoiding the extrapolation failure from the previous attempt (logged 2026-09-08 earlier). Applied that lookup to every real 2013 household-night by matching its own real temperature, and computed demand-weighted totals directly from real per-household kWh.

**Result — a genuine, defensible number, not a proxy estimate.**
- Demand-weighted mean grid intensity for real storage-heater consumption timing: **142.7 gCO2/kWh** (bin-extreme range 63.6-211.8).
- Per household per year (real 4,721 kWh average heat demand): **gas 958 kg CO2, storage heating (actual real behaviour) 735 kg, storage heating (perfectly managed) 676 kg, heat pump at real field SCOP 2.78 243 kg.**
- So: storage heating genuinely beats gas on carbon by about 23% on this real demand-weighted average — a real, if modest, edge, not the illusory artefact the flawed proxy attempt manufactured. But real night-to-night volatility inside each temperature/wind band is large (e.g. the 2-4°C band alone ranges 65.6-275.5 gCO2/kWh across real observed nights) — using each bin's own worst observed value instead of its mean, 67.7% of the fleet's real kWh would fall on nights whose bin has touched a carbon intensity above gas, versus only 1.1% using bin averages. That gap is the honest, quantified version of the original 23-night finding: the *average* cold night is fine, but a materially large share of real winter heating happens in temperature/wind conditions capable of running dirtier than gas.
- Heat pump wins decisively under every framing: ~75% lower carbon than gas on the central estimate, and still clearly ahead even using the most pessimistic per-bin extreme.

**Honest limitation.** Most 2°C bins now hold 3 real nights (up from the previous attempt's single narrow band), a real improvement, but still a modest sample per bin — tightening this further (aiming for 6-10 real nights per bin) is a legitimate next increment if a tighter confidence interval is ever needed, but the qualitative and headline findings above are stable enough to publish as-is.

**Bottom line for Post 5 / the roadmap:** the earlier draft's honest hedge ("I haven't done the demand-weighted calculation yet, it could be lower or worse than gas") is now resolved with real data — storage heating's carbon edge over gas is real but modest on average, masks a real and quantifiable volatility risk, and none of this changes the heat pump conclusion, which strengthens further under the same real-data standard.

## 2026-09-08 — Route B corrected: fixed a real BST timezone bug and bin sparsity, result holds

External review (feedback on the Route B methodology) flagged five points. Two were real bugs, checked and fixed; three were valid caveats that don't change the number.

**Confirmed non-issue, but worth recording:** `mean_temp_c` in the household dataset is a full calendar-day mean (joined from `london_weather_2013.csv` by date, per `pipeline_stage2_nightly.py`), not restricted to the 23:00-07:00 night window. However, the Route B sample nights were characterised using Open-Meteo's daily mean temperature too, so the two sides of the bin-lookup join use a consistent definition — this isn't a Route-B-specific bias, it's a pre-existing feature of the whole project's `heat_loss_proxy` design from Stage 1 (daily mean temp as a proxy for the temperature driving overnight heat demand).

**Confirmed real bug #1 — BST timezone shift.** All Carbon Intensity API fetches used a literal `T23:00Z`/`T07:00Z` window. During BST (late March-late October) this is actually 00:00-08:00 local, not 23:00-07:00 -- a 1-hour shift. 14 of the 31 new sample nights fell in BST. Spot-checked the size of the error: negligible on a flat night (2025-06-23, 58.1 vs 58.9 g/kWh, ~1%), but real on a night with a sharp dawn ramp (2025-04-27, 126.4 vs 116.4 g/kWh, ~8.6%). Fixed: refetched all 14 BST-affected nights at the correct `T22:00Z`/`T06:00Z` window and replaced the values in `route_b_recompute.py`.

**Confirmed real bug #2 — bin sparsity.** The original 2°C bins left several with only 1-3 real nights (one bin had n=1), too thin to trust a mean or extremes from. Fixed: widened to 4°C bins (6 bins total, n=3 to n=20; only the coldest tail bin, carrying ~5% of real kWh, is still at n=3). Also switched the reported "range" from raw bin min/max (which becomes close to meaningless once n exceeds ~5, since some outlier is almost guaranteed) to a 10th-90th percentile band, per the review's recommendation -- meaningful now that most bins have enough nights for percentiles to differ from the extremes.

**Result after both fixes:** the headline numbers barely moved -- demand-weighted mean intensity 143.1 g/kWh (was 142.7); gas 958 kg/household/yr (unchanged); storage heater actual 738 kg (was 735); storage heater managed 678 kg (was 676); heat pump 244 kg (was 243). The volatility caveat is now reported on a defensible percentile basis instead of a degenerate bin-extreme one: 33% of real fleet kWh sits in bins whose 90th-percentile night exceeds gas, versus 0% on the mean or 10th-percentile basis. No household's demand-weighted mean individually exceeds gas.

**Bottom line:** the fixes were real and worth doing -- they replace two genuine methodological holes with a more defensible construction -- but they didn't change the conclusion. Storage heating's ~23% carbon edge over gas is confirmed real and now more robustly measured; the heat pump's advantage (a quarter of gas, a third of storage heating, and zero households crossing gas even at their own individual demand-weighted mean) is unaffected and remains the strongest, most robust finding in the whole comparison. Post 5's numbers do not need revising again.

## 2026-09-08 — Route B correction #2: found and fixed a wind-selection confound pooled into the temperature bins

Spot-checked the corrected Route B chart and noticed the -4 to 0C bin sat *below* the 0-4C bin in mean carbon intensity -- backwards from the intuitive expectation that colder nights draw more fossil generation. Investigated rather than dismissed as noise.

**Root cause, confirmed by checking wind speed composition per bin:** the original 23-night sample was selected on cold AND still (`heat_loss_proxy>10 & wind<8km/h`) -- a joint condition, not temperature alone. Those 23 nights cluster in the 0-4C band (14 of 23) and all share the deliberately-low-wind selection criterion. Pooling them with the 31 new nights (which were sampled with low/median/high wind *within* each temperature bin, an unconfounded design) left the 0-4C bin 70% populated by artificially-calm nights: mean wind 7.4 km/h there, versus 10.8 km/h in the 4-8C bin and 12.8 km/h in the 8-12C bin -- a monotonic real relationship being disrupted by one bin's biased composition. Since wind (renewable output), not temperature, is carbon intensity's real driver, this pulled the 0-4C bin's mean carbon intensity up to 168 g/kWh, higher than its warmer AND colder neighbours -- an artifact of sample composition, not a real cold-weather effect.

**Fix:** rebuilt the bin lookup from only the 31 new, wind-balanced nights. The original 23 are kept as an explicitly-labelled worst-case reference (real cold/still nights, 35% individually exceed gas) rather than folded into the demand-weighted average.

**Corrected result (supersedes both prior Route B write-ups):** demand-weighted mean intensity 131.5 g/kWh (previous corrected value: 143.1; original naive estimate: much higher). Gas 958 kg/household/yr (unchanged -- fixed efficiency). Storage heater actual 678 kg (previous: 738). Storage heater managed 621 kg (previous: 678). Heat pump 223 kg (previous: 244). Volatility: on the unbiased sample, 0% of real fleet kWh sits in bins whose 90th-percentile night exceeds gas (previous corrected figure: 33%) -- the earlier volatility estimate was itself inflated by the same confound. The 35%-of-nights-exceed-gas finding from the original cold/still sample is retained but now correctly labelled as a deliberately adverse reference case, not the typical/average picture.

**Why this one moved the headline numbers more than the BST and bin-width fixes did:** those two were precision fixes (a few percent each); this one removes an actual bias baked into the sample's composition, so the correction is larger (~8-10% depending on the line) and changes the volatility framing meaningfully -- honest storage heating still beats gas by more than gas, more decisively than the last write-up suggested, but the "how volatile is this really" answer moved from "meaningfully risky" to "not really volatile, once wind is sampled fairly." Both the current bin-based estimate and the cold/still reference case are real and worth keeping side by side: one answers "what's the average," the other answers "what does a bad stretch look like."

**Standing lesson for the rest of this project:** when a "real, non-cherry-picked" sample is built by combining data collected under different selection rules, check the composition of every downstream bin/group for a hidden skew before trusting a comparison across it -- this is the second time this session that a plausible-looking real-data result turned out to hide a construction artifact (the first being the BST timezone bug), and both were caught by scrutinising the result rather than accepting a number because the method sounded rigorous.
